01Email triage·US appraisal management company

95% of incoming email handled without a person reading it

The problemThe intake desk received 700 to 1,300 emails a day from appraisers, lenders and borrowers. The old keyword rules sorted about half. Staff read and routed the rest by hand, every day.

What I didRebuilt the sorter as an AI pipeline that reads each email, answers the questions the team used to answer by eye, and files it to the right queue. Then tuned it for a year against the QC team’s daily corrections.

What changedAuto-resolution went from 50–60% to 95%. The share of mail a person has to read and route fell from roughly 45% to 5%. Runs on the company’s own GPU servers.

50–60% → 95% auto-resolved700–1,300 emails / dayon-premise
How it works

Each email is answered against about 15 classification questions, each with 2–4 labels, across four recipient roles (appraiser, lender, borrower, point of contact). The answers merge into one routing decision.

Question routing. An offline embedding index over labelled example phrasings ranks all 15 questions against the incoming email; only the top 7 reach the LLM. That roughly halves model calls per email and removed the throughput bottleneck that appeared as the question set grew.

  • Temperature 0, so output is reproducible and testable.
  • Per-question hard timeouts that fail loudly instead of hanging.
  • Signatures, legal disclaimers and marketing footers stripped before classification.
  • Merge safeguards so fee and payment requests are never dropped.

The gain came not from a better prompt but from deciding, per email, which questions were worth a model call at all.

Python · gpt-oss:20b via Ollama · LangChain · nomic-embed · fully on-premise

02Voice & text agent·Built solo

A phone assistant that answers the same requests all day, on one GPU

The problemCallers phone in with the same handful of requests. The assistant had to run on a single GPU, with no cloud AI and no customer data leaving the building.

What I didOne conversation engine shared by phone and text. It recognises the caller from their number, greets them by name, looks up their orders and handles 32 kinds of request across appraisers, lenders and borrowers. It also places outbound calls and can tell a voicemail from a person.

What changedMost routine requests get a correct answer in about a tenth of a second with no model call at all. Where the model is needed, it is asked only then. Every error in testing came from the model path, which is exactly where to keep working.

32 request types · 3 caller roles~115 ms no-model path100% on the fast path
How it works, and the numbers

Confidence-gated routing. One LangGraph state machine handles caller identification, order lookup and routing across 32 tools and three caller roles, shared by voice and text so the logic exists once.

  1. Embed the caller’s sentence; retrieve the five nearest tools by cosine similarity.
  2. Sharpen the scores with a low-temperature softmax (T = 0.08).
  3. Measure confidence as normalised Shannon entropy.
  4. If entropy ≤ 0.45, answer directly with no model call.
  5. Otherwise let the LLM re-rank the candidates.

Call experience. Silero VAD tuned so a spoken street address, which has pauses, is not cut into fragments. Caller identified from the phone number and greeted by name. Fixed replies pre-rendered to cached audio, short fillers cover slow database lookups. Every order is scoped to the caller with ownership checked before anything is read out. Roughly six sequential model calls per turn.

Outbound. LLM-based voicemail-versus-human detection: a machine gets a complete message and a hang-up, a person gets a conversation. Real inbound phone calls are bridged into the same engine through Twilio Media Streams.

A deterministic path is worth building even when a model could do the job. Here it was both the fastest and the only error-free route.

03Document routing·Appraisal reports

Every incoming report lands in the right review queue by itself

The problemAbout ten kinds of appraisal report arrive in one stream, and several of them use almost the same words. The QC team sorted them by hand, file by file.

What I didTrained a classifier that looks at the page layout, not only the text, because the look-alike types differ in structure: where the tables sit, the headers, the signature blocks. Rebalanced a heavily skewed dataset before training.

What changedEach document is routed automatically, with 90–98% accuracy per class, trained on about 10,000 PDFs.

90–98% per class~10 report types~10,000 PDFs
How it works
  • Layout-aware model (LayoutLMv3) chosen over text-only classification because several report types share vocabulary and differ mainly in structure.
  • Majority classes downsampled; minority classes augmented with noise, flips and rotation.
  • OCR via PaddleOCR.

LayoutLMv3 · PaddleOCR · Python

04Property photo check·54 classes

Confirms every required property photo is there before a human looks

The problemEach report must include a photo of every area the appraiser inspected. Missing or mismatched photos were caught by eye, when they were caught.

What I didA 54-class image classifier trained on more than 500,000 images, and a monthly loop: QC flags wrong predictions during normal review, I relabel and retrain, so accuracy holds as new property types appear.

What changedMissing and mismatched photos are flagged for QC automatically, above 90% accuracy per class.

>90% per class500,000+ imagesmonthly retraining loop
How it works

YOLO classification model. The improvement loop matters more than the first training run: the client’s US QC team reviews output daily, their corrections become the next training set, and per-class accuracy is checked, not only the aggregate.

YOLO (classification) · Python

05Signature detection·First production project

Catches unsigned reports before they move downstream

The problemReports need specific signatures before anything else can happen. Unsigned ones used to slip through and bounce back later.

What I didThe first version used classical computer vision only, because no suitable detector was available to me then. Later I migrated it to a trained detector, which is easier to maintain and retrain.

What changedUnsigned reports are caught at intake instead of downstream.

classical CV → YOLOin production
How it works
  • Morphological removal of ruled lines, OCR boxes to suppress printed text, FFT analysis to isolate irregular signature regions.
  • Migrated to a YOLO detector once one could be trained on the client’s data.

OpenCV · OCR · FFT → YOLO

How I work

Five habits behind every number above.

Requirements come from people who own the work, not from a spec. Errors come from real reviewers, not synthetic tests. And the ugly split gets reported.

Frame it with the people who own it

Requirements come from non-technical staff. My job is turning them into label definitions a model can follow.

Collect real errors, not synthetic ones

The client’s QC team reviews output daily. Their corrections become the next training set.

Rebalance before retraining

Real data is skewed. Check per class, not only in aggregate.

Change the rule when the edge case is right

Sometimes the model is correct and the label definition was wrong.

Report the ugly split too

Clean vs messy input, per class and per role. An average hides exactly what needs fixing.
