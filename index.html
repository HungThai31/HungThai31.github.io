The method is confidence routing.

Retrieval answers when it is sure; the model is called only when it is not. Fewer calls, lower latency, and fewer errors — measured, not assumed.

The through-line

Every system here runs on company GPU with no cloud AI. That constraint is what forced the interesting idea: model calls are a budget, so spend them only on genuine uncertainty.

Why it needed a router, not just a prompt

Fifteen questions per email, each with 2–4 labels, across four recipient roles. As the question set grew, throughput — not accuracy — became the ceiling.

  • Rank before asking. An offline embedding index over labelled example phrasings scores all 15 questions against the incoming email.
  • Only the top 7 reach the model. The other eight never run, which roughly halves calls per email.
  • Merge with safeguards. Fee and payment requests can never be dropped when answers are combined.
  • Clean the input first. Signatures, legal disclaimers and marketing footers are stripped, or they poison the classification.
  • Fail loudly, never hang. Per-question hard timeouts, because nobody is watching it at 3 a.m.

The decision rule

Calling the model on every sentence is slow and, measurably, where the mistakes live. So the router asks a cheaper question first: is retrieval already sure?

  1. Embed and retrieve the five nearest tools by cosine similarity.
  2. Sharpen those scores into a distribution — low-temperature softmax T = 0.08.
  3. Measure confidence as normalized Shannon entropy. Peaked means sure; flat means unsure.
  4. Answer directly below the threshold H ≤ 0.45, with no model call at all.
  5. Defer above it, and only then let the model re-rank the candidates.

The threshold is a risk–coverage trade-off: push coverage up only while the accepted set stays clean.

What happens during a call

  • Patience is tuned, not default. Silero VAD waits long enough that a spoken street address — which has pauses in it — is not chopped into fragments.
  • The caller is known before they speak. Identified from the number, then greeted by name.
  • Silence is designed away. Fixed replies are pre-rendered to cached audio; short fillers cover slow database lookups.
  • Every order is scoped to the caller, with ownership checked before anything is read out.

05How I work

A model is only as good as the loop around it.

None of these were finished at launch. What keeps them accurate is a repeatable cycle — and a willingness to change the label definitions, not just the weights.

  1. Frame it with the people who own it. Requirements arrive from non-technical staff; my job is turning them into label definitions a model can follow.
  2. Collect real errors, not synthetic ones. The client's US QC team reviews output daily; their corrections become the next training set.
  3. Rebalance before retraining. Real data is skewed — downsample the majority, augment the minority, and check per class, not only in aggregate.
  4. Change the rule when the edge case is right. Sometimes the model is correct and the definition was wrong.
  5. Report the ugly split too. Clean input versus messy input, per class and per role — an average hides exactly what you need to fix.
Delivery reality

Models live inside someone else's application

Every model ships as a Python service invoked by the company's PHP application under www-data — filesystem permissions, environment isolation, and clear error and exit-code contracts between two runtimes. Long jobs run under systemd.

Infrastructure

I own the machines too

Three Ubuntu GPU servers running all ML workloads — CUDA and driver setup, monitoring, fault diagnosis — plus MariaDB master–slave replication across three replicas, including resync after a replication break.

Why it matters

Nothing here was handed to a platform team. Being the only engineer meant the evaluation loop had to be simple enough that I could actually keep running it.
